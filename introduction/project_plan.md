# 异构设备上的 PoW 区块链与并行计算性能评估

**English title:** Design and Performance Evaluation of a PoW Blockchain on Heterogeneous Devices

- 文档日期：2026-11-07
- 项目类型：Computer Organization and Architecture 四人课程设计
- 文档状态：单节点及本机多进程网络阶段已在 MacBook 验证；其他设备、优化和仿真仍待实现；本地 HTML 观测台已实现
- 运行环境：封闭局域网，软件与依赖提前安装，运行和演示无需外网
- 仓库名称：[Xiejz959/COAP_BlockChain](https://github.com/Xiejz959/COAP_BlockChain)，不与协议或程序路径绑定

## 1. 项目目标

在 MacBook、PC 和 Raspberry Pi 5 上运行独立区块链节点。各节点执行 SHA-256 PoW 计算、验证区块、交换消息并维护本地区块链，通过统一规则选择当前采用的链。

每增加一个被当前链接受的非创世区块，累计区块数增加 1。累计区块数用于观察多节点进度与一致性，不表示账户余额、资产或计算收益。

以这个可运行的系统为应用载体，比较不同设备、计算实现和 CPU 核数的性能，分析本地并行计算与节点间通信对整体系统的影响。

## 4. 硬件与部署

### 4.1 开发顺序

1. MacBook 与 PC 先完成双节点运行。
2. 加入 Raspberry Pi 5，开展 ARM 原生计算与多核实验。
3. 有条件时增加其他 PC，完成约四节点课堂演示。

协议不依赖固定的节点数量。MacBook 的处理器架构和 PC 的操作系统以实际设备为准，不预先假定。

### 4.2 网络

所有设备连接同一台独立路由器，路由器不连接外网。节点使用配置中的局域网 IP 和端口通信。

首版使用手动配置的种子节点地址和节点列表，不依赖 Tailscale、外部节点发现服务或自动局域网扫描。种子节点只帮助建立连接，不具有区块有效性或选链决定权。

依赖、编译工具和所需软件在实验前安装；正式运行不下载资源、不调用外部 API。验收时断开路由器外网，验证冷启动、节点连接和浏览器面板仍正常工作。

### 4.3 基准运行方式

使用宿主机原生进程进行部署和性能测量，不使用 Docker，统一协议和工作负载。MacBook 已建立 Python 3.11 的独立 `blocknode` Conda 环境，环境配置位于 `codes/environment.yml`；其他设备的安装仍需验证。记录操作系统、CPU 型号、核心配置、编译器、库版本及实际运行条件。

## 5. 区块与共识方案

### 5.1 最小区块

单节点版本已实现协议版本、网络标识、前一区块哈希、区块高度、节点标识、全网目标值和 Nonce。创世配置定义统一 PoW 目标值。区块不包含交易、账户或奖励数据。

字段宽度、字节序、哈希输入顺序和数值范围已固定，详见 [协议说明](protocol.md)。固定创世哈希有自动测试核对，跨平台运行仍待验证。浏览器展示格式不作为共识序列化格式。

节点名称用于监控与连接标识，不是钱包地址，也不作为授权出块的凭证。

### 5.2 PoW 计算

每个计算节点根据当前链头构造候选区块，搜索使 SHA-256 结果不大于目标值的 Nonce。各节点不必全部参与计算，也可以只验证和同步。

当前为 Python 单进程参考实现。后续同一节点内的计算工作线程使用互不重叠的 Nonce 搜索范围。节点之间独立进行 PoW 搜索，不引入计算池或集中任务分配服务。链头改变后，计算节点应切换到新链头上的候选区块。

首版使用固定且全网一致的难度；不同设备不能自行降低难度。所有计算后端输出相同协议下的有效区块，不改变区块有效性规则。

### 5.3 区块验证

节点独立检查：网络和协议匹配、字段和序列化有效、父区块存在、高度为父块高度加 1，以及 PoW 满足统一目标值。

当前已实现重复区块不重复计数，非法区块明确拒绝，不自动放宽协议条件。允许已知父块上的有效分支；网络层遇到缺少父块的区块后分批获取有序祖先并验证，未完成验证的区块不进入存储图或当前链。

### 5.4 选链与分支

本节规则已实现，并通过本机 TCP 分支收敛和重启持久化测试。尚未验证真实设备网络分区。

节点仅在有效区块组成的候选链之间比较累计工作量。固定目标值下，每个区块的协议工作量相同，因此累计工作量较大的链也具有更多区块；不能通过声明更高高度或更高工作量绕过验证。

累计工作量相同时，暂时保留当前链头并保存另一有效分支，等待后续区块打破平局。因此，不承诺重新连接后在没有新块的情况下立即选择同一分支。受控演示应在一个分支增加区块后检查收敛。

接纳一个延伸当前链头的区块时，可观察到累计区块数加 1。发生分支切换时，从新采用的链重新计算状态，不把两个分支上的块数相加。

### 5.5 累计量定义

`accepted_block_count = current_chain_height`

创世块高度为 0，不计入累计量。累计量由当前采用的链派生，无单独的“积分计数器”，也不存在按节点分配的余额。

例如，创世块之后依次接纳三个区块时，累计量依次为 1、2、3。高度相同的两条链可能内容不同，所以界面和验收必须同时比较累计量及链头哈希。

PoW 具有概率性，四个实验节点不构成生产环境安全保证；本项目验证的是已定义规则下的受控实验行为。

## 6. 软件模块边界

以下为完整项目的职责划分。当前已实现 Chain 的编码与验证、Compute 的单进程计算、Storage 的区块图与选链、Network 的 TCP 消息同步及终端入口；本地只读监控已实现；优化和性能实验仍待实现。

| 模块 | 职责 |
| --- | --- |
| Protocol / Chain | 创世配置、确定性编码、区块验证、选链和累计量派生 |
| Compute | 原生 Nonce 搜索、计算后端和节点内多核执行 |
| Network | 手动节点配置、消息传递、广播、缺块获取和重连同步 |
| Storage | 保存区块与链头，重启后读取并恢复状态 |
| Telemetry / Dashboard | 节点状态、链头、累计量、算力和系统资源展示 |
| Experiments / Simulation | 基准执行、原始结果记录、参数模型和出块事件仿真 |

Python 用于协议组织、网络、实验和监控；C/C++ 用于性能关键计算；持久化优先考虑 SQLite。接口与依赖在开始实现时确定，仅加入实际需要的组件。

SHA-256 使用成熟实现。通用实现与 ARM 加速实现必须明确实际执行路径，不能把 Python 调用与 C 调用的耗时差直接归因于指令集。协议不增加自定义密码算法。

当前 Nonce 循环在 Python 中调用标准库 SHA-256，用于验证最小闭环，暂不作为最终优化后端。后续将循环放在原生计算层批量执行，避免逐次跨语言调用。并行方式需避免由 Python 解释器锁限制 CPU 利用率。

## 7. 性能实验

### 7.1 实验一：计算实现对比

在同一 Pi 上，用相同区块格式、输入规模和单核条件比较通用原生 SHA-256 与使用已验证 ARM SHA 指令的实现。

指标为固定工作量耗时、每秒哈希次数和加速比；系统支持并已验证计数器时，再报告 CPU 周期等硬件指标。记录库版本、编译参数及实际加速路径，不预先承诺提升幅度。

### 7.2 实验二：节点内多核扩展

Pi 分别使用 1、2、3、4 个核计算相同总量的候选区块。记录哈希吞吐、加速比、并行效率、CPU 使用率、频率和温度。

总工作量和输入保持一致。以单核为基线，分析线程管理、共享资源及热行为对扩展效率的影响。

### 7.3 实验三：异构设备对比

在 MacBook、PC、Pi 上运行相同固定工作量，先比较单核，再单独比较实际配置下的多核表现。

不同设备的结果属于平台对比，不能仅凭一次跨设备跑分推出 ARM 或 x86 指令集的普遍优劣。

### 7.4 实验四：完整节点中的计算与通信

比较 Pi 不参与 PoW、使用一个核参与 PoW、使用四个核参与 PoW 时的节点行为。

记录本地哈希吞吐、区块验证耗时、接收区块后的处理延迟、CPU 和内存占用。通过发送方与接收方事件日志观察传播和恢复过程；跨设备单向时间差必须有时钟同步依据，否则使用往返测量或各设备本地时长。

研究更多计算资源是否同时影响区块验证和同步，而不把更高哈希吞吐直接解释为更高应用吞吐。

### 7.5 测量规范

- 哈希基准执行固定数量的 Nonce，不用首次找到有效区块的等待时间代替确定性跑分。
- PoW 出块使用重复随机实验，报告观察时长、样本数及离散程度。
- 记录基线、输入、预热、运行次数、硬件与软件配置以及散热条件。
- 保留原始结果；没有实际测量的数据不填充为实验结论。
- 网络条件单独记录，区分本地计算耗时、通信耗时和共识收敛。

## 8. Simulation 方案

### 8.1 节点内并行性能模型

以固定工作量单核耗时为基线，采用串行部分、可并行部分和并行开销组成的模型：

`T(N) = T(1) × [(1 - P) + P / N] + overhead(N)`

使用部分实测配置校准参数，在未参与校准的核数或工作量上检验预测误差。模型用于解释扩展趋势，不声称逐周期复现 Cortex-A76，也不把网络仿真称为 CPU 微体系结构仿真。

### 8.2 出块与传播事件仿真

将实测的各节点哈希吞吐作为输入，建模区块发现、消息传播、区块验证和分支延伸事件。变化参数限定为设备算力与节点间延迟。

在均匀独立哈希和固定目标值假设下，节点发现有效结果的速率由“每秒哈希次数 × 单次成功概率”给出。仿真报告这些假设，不用仿真代替真实哈希实现验证。

输出平均出块间隔、临时分支发生情况和收敛时间，并与真实节点重复实验对照。原始硬件结果与仿真输出分别标注。仿真模型是否满足教师对 Simulation 的具体要求，应以课程反馈为准。

## 9. 展示与验收

监控页面采用 HTML/CSS/浏览器原生 JavaScript，不使用 Node.js、npm 或前端框架。页面只包含节点列表、连接状态、当前高度、链头哈希、近期区块、PoW 开关与执行状态、哈希吞吐和资源指标。静态页面资源本地提供，不依赖在线 CDN。

| 场景 | 验收依据 |
| --- | --- |
| 双节点基础运行 | 一个节点出块，另一节点独立验证；两端高度和链头一致 |
| 多节点运行 | Pi 与 PC 接入同一网络，保持相同协议和创世配置 |
| 重启 | 从本地存储恢复区块和链头，继续同步 |
| 断线恢复 | 节点重连后补齐并验证缺失区块，最终链头一致 |
| 无效与重复区块 | 拒绝非法区块；重复广播不重复增加累计量 |
| 受控分支 | 保存并验证分支；一条分支工作量更高后按规则切换并收敛 |
| 架构性能展示 | 展示同负载下不同计算实现与核数的实际结果 |
| 离线运行 | 路由器不接外网时仍能冷启动、通信、出块和查看面板 |

## 12. 开发里程碑

1. **协议与单节点：** 固定区块编码及创世配置，完成 PoW、验证、持久化和累计量派生。

4. **仿真与性能分析：** 校准模型、执行独立验证实验，整理原始结果和误差分析。
5. **监控与离线演示：** 接入实际测量，完成断线恢复、受控分支与完整课堂演示。
